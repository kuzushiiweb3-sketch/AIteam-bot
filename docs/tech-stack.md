# Tech stack: languages, libraries, storage format and testing

**Status: PROPOSED** by the data engineer, 2026-11-05. Red-team still has to attack it before it is adopted (CLAUDE.md rule 7; TODO "red-team attacks it"). Nothing in this file signs, sends or simulates a transaction.

## In plain English (for Paul)
- The parts that run all day and handle money maths will be written in **Rust**: the recorder, the decoders, the fee maths, the monitors, the paper simulator and, in Phase 3, the guard. Rust is a strict, fast language. It catches many mistakes before a program ever runs, and it does exact maths on the very large whole numbers Pump.fun uses.
- Research and statistics will be written in **Python**, the standard tool for data analysis. Python only reads the finished data files. It never talks to a wallet and never has its own copy of the fee maths.
- Pump.fun's own toolkit is written in TypeScript. We use it **only inside tests**, as an independent referee for our maths. It never runs in the bot.
- Recorded market history is kept in two forms. One is the exact bytes we received, so we can re-read them after Pump changes something. The other is tidy tables (Parquet files) that research can search quickly. There is no database server to run or secure.
- **Cost: $0.** Every tool is free and open source. Every outside package is pinned to an exact version and must be at least 7 days old before we use it, because poisoned packages are usually caught within days. I tested that rule today on two of the package tools, and it works.

[VERIFIED-LOCAL] = I ran it in this environment today. [UNVERIFIED] = judgment or memory; the settling test is named. [DERIVED] = arithmetic on tagged inputs. I used 6 web searches. ## 3. Why this split
1. **Priority 1 (no losses to bugs or bad data) decides it.** The two-witness check and T6 demand maths "to the last unit" on `u64` and `i128` values [VERIFIED-DOC IDL]. Rust makes those types explicit and can refuse to wrap on overflow. JavaScript needs perfect `bigint` discipline in every line, which is the kind of rule AI-written code breaks quietly [DERIVED].
2. **The recorder must never fall behind and can't be rebuilt honestly later** (rulings §7). The reference Yellowstone client is Rust [VERIFIED-DOC]. Even the TypeScript client is Rust underneath [VERIFIED-SEARCH].
3. **Our design deliberately avoids Pump's SDK in the money path** (DESIGN decision 4; SEC-5). So TypeScript's one big advantage, the official SDK, matters only as a referee in tests. We get that for free, offline, through `tools/sdk-oracle/`.
4. **Research needs Python's tools**, but Python never needs a Solana library. Decoding happens in Rust, and Python reads typed Parquet files. That removes `solders`, `solana-py` and `anchorpy` from the project entirely.
5. **Keeping the money code in one language** means the guard (Phase 3) can reuse the exact fee, pool and decoder crates that T6 validated. The safe-mode seller deliberately does not reuse them (§5j).

## 4. Attacks I expect, and the answers (for red-team to push on)
1. **"Rust will slow you down."** Research iterates in Python. Rust changes only when a new feature or rule *primitive* is needed, and the decoders are generated. Fallback trigger: if the Rust recorder can't record 24 h with no unexplained gap by the end of Phase 1 week 1, swap **only the recorder process** to the TypeScript napi client (S2). That swap is cheap because the raw tape format (§6b) is language-neutral protobuf frames, so decoders, `tabulate` and research don't change.
2. **"Two languages means two fee models."** The fee and pool maths exist only in `crates/fees`. Python gets fee-derived numbers as columns written by Rust, or by calling `desk-sim quote`. A CI check fails if `research/` contains fee constants or basis-point arithmetic (a simple text scan). An optional Python binding of the same Rust code (PyO3) is allowed later, but never a rewrite.
3. **"Rust's Solana dependency trees are huge."** Production crates don't use `solana-client`, `solana-sdk`, Anchor or `carbon-*`. `cargo-deny` bans them (§9). The Yellowstone proto crate brings in only `prost`, `prost-types`, `siphasher`, `solana-pubkey` and `thiserror` [VERIFIED-DOC crates index].
4. **"The Yellowstone client changes major version every ~10 days."** We pin an exact version, wrap it behind our own small `feed` interface, and upgrade at most monthly, only when the replay and reconnect tests (C04/D8) pass.
5. **"The referee pulls npm and native binaries onto your machine."** It is test-only, runs with an empty environment (`env -i`, no keys), never on the bot host's service user and never on the guard, under pnpm's strictest settings (§9).
6. **"Same language for guard and safe-mode seller means shared bugs."** See §5j: separate crate, separately written code, differential tests. Red-team may require Go for the seller instead.
7. **"Parquet has no 128-bit integer."** We store `i128` as `Decimal128(38, 0)`, with an alarm if a value's magnitude reaches 10^38 (impossible for lamport-sized reserves [DERIVED]). Test STK-2 proves the round trip in DuckDB and Polars.
8. **"Research jobs will starve the recorder on one server."** Every process runs under systemd with CPU and memory limits. Research gets low priority and its own memory cap; the recorder gets top priority and its own disk (DAT-8) [UNVERIFIED limits; tuned in Phase 1].

## 5. Component by component

### 5a. Recorder (`crates/recorder`)
- One process per provider stream. It does almost nothing: receive, timestamp, frame, append, fsync, and answer the server's ping [VERIFIED-DOC README: server pings every 15 s].
- It does **not** decode. Decoding happens in `tabulate`, so a decoder crash can never stop recording.
- It writes control frames too: connect, disconnect, the subscribe request (the exact filter used), ping/pong and gap markers.
- Its own disk, with the 70/85/95% alarms (DAT-8).

### 5b. Decoders (`crates/idlgen` → `crates/decoders`)
- **Input:** the pinned `pump.json`, `pump_amm.json` and `pump_fees.json`, with their SHA-256 and the `pump-public-docs` commit they came from.
- **Generator output** (Rust, committed to the repo, marked "GENERATED, do not edit", regenerated in CI, which fails on any difference):
  - account structs with exact-length decoding plus an **allowed-lengths table per version** (shorter older layouts read missing trailing fields as 0, per NEW-8);
  - event structs;
  - instruction-argument structs.
- **Dispatch always keys on the program first**, then the discriminator. `buy_v2` has the same discriminator in both programs [VERIFIED-DOC].
- **Events are read from inner instructions**, never only from logs (logs get cut off). An event call starts with the 8-byte Anchor event tag `e4 45 a5 2e 51 cb 9a 1d` (the little-endian form of sha256("anchor:event")[..8] = `0x1d9acb512ea545e4`) [DERIVED; test A04/D5 confirms], then the event discriminator = sha256("event:<Name>")[..8]. That matched the IDL for every event I checked [VERIFIED-DOC, computed locally].
- Any unknown discriminator from a watched program raises `UNKNOWN_EVENT`. Its raw bytes are stored and new buys pause. It is never skipped.
- **Hand-written layer:** the two-witness check, reserve continuity, and the dormant-field monitor (DAT-1).
- **Why our own generator instead of Codama or Anchor's macros:**
  - we need exact-length and version rules that those tools don't provide;
  - Codama's event support is unconfirmed [UNVERIFIED];
  - Anchor's macros drag in the whole Anchor and Solana 2.x crate tree [VERIFIED-DOC index].

  A Codama-rendered Rust client may be used as a **test-only cross-check**.

### 5c. Fees and pool maths (`crates/fees`)
- Integer-only (`u64`/`u128`/`i128`), checked arithmetic: an overflow is an error, never a wrap.
- Implements `docs/fee-model.md` §3 exactly.
- Validated by T6 (test-plan row A09) and the SDK referee vectors. Property tests check, for example, that output never exceeds the reserves and that fees never go negative.

### 5d. Forensics and coin state (`crates/forensics`)
- Built from the stream: dossiers, the insider ledger with plain-transfer following, the holder map, and theme waves (code-only first).
- State is in memory with periodic snapshots to SQLite, so a restart rebuilds quickly.
- Funding lookups are queued RPC calls, never in the decision path.

### 5e. Monitors (`crates/monitors`)
- Slot-lag check (Helius `slotSubscribe` vs the Chainstack slot stream), heartbeat, silent-feed probe, coverage audits with the four keys, admin/program/IDL watch (hourly IDL hash from `raw.githubusercontent.com`), and the Helius credit meter (SQLite).
- JSON-RPC is done with plain `reqwest` + `serde_json`, not `solana-client`. That avoids 30+ dependencies and the rustc 1.98.1 requirement [VERIFIED-DOC index].

### 5f. Strategy engine and paper simulator (`crates/strategy`, `crates/sim`)
- **One engine, two callers:**
  - the `sim` command-line tool replays the tape for backtests and pre-registered tests;
  - the Phase 3 paper bot runs the same engine on the live stream.
- Rules are data (TOML/JSON in the fixed rule language). The engine writes one reason-coded log line per decision (DESIGN §2b.4).
- **Confirmatory tests run only through `desk-sim`**, with frozen rule files, seeds and data windows, hashed into `docs/preregistration.md`. Python may explore freely, but a pass mark is only ever earned through the Rust simulator.

### 5g. Research and backtests (`research/`, Python)
- `polars` and `duckdb` over the Parquet tables; `numpy`/`scipy` for the day-block bootstrap and other statistics.
- Each study is a script, not a notebook, so it can be re-run and diffed.
- It writes `reports/daily/YYYY-MM-DD.md`.

### 5h. AI desk and rule-change reader (Python)
- The official `anthropic` SDK, pinned.
- A refusal or timeout means "no decision" (brief, Claude prices section).
- The AI's output is a rule file, validated by `desk-sim validate` before it can enter shadow testing. The rule-change reader is triggered by the IDL-hash monitor.

### 5i. Dashboard (Phase 3)
- Rust `axum`, server-rendered, no npm build. Decided in Phase 3. The later "striking live visual" product is out of scope here.

### 5j. Guard, signer, safe-mode seller (Phase 3; provisional; red-team decides)
- **A separate Cargo workspace** with its own lockfile. Dependencies are vendored (`cargo vendor`) and every line of the vendored diff is reviewed on update.
- **The guard** reuses `decoders` + `fees` (the T6-validated code) and builds every transaction itself from the pinned IDL. Signing is through AWS KMS [VERIFIED-SEARCH via SEC-R]; AWS SDK for Rust versions are UNVERIFIED until Phase 3.
- **The safe-mode seller** (rulings R1: "deliberately different code"):
  - its own crate, with its own small sell builder and constant-product min-out maths written separately;
  - no shared code with the guard except the pinned IDL JSON and the golden vectors;
  - **differential tests**: for the same inputs, both builders must produce byte-identical sell instructions, and min-outs must agree within 1 lamport.

  This gives independent code without a second toolchain on the guard account. **Open question for red-team:** is that enough, or should the seller be written in Go (`solana-go` v1.26.0 [VERIFIED-DOC]) for language diversity?

### 5k. Phase 0 scripts (`phase0/scripts/`, next TODO item)
- **Network fetchers:** Python **standard library only** (`urllib.request`, `json`, `ssl`, `hashlib`, `base64`, `time`). They are read-only, rate-limited, never print keys, and save raw responses with a provenance file.
- **Analysis that decodes Pump data or does fee maths** runs offline in the Rust `decoders` + `fees` crates over those saved fixtures. Those two crates are therefore built in Phase 0. They only read, which is allowed (CLAUDE.md rule 2).
- Python may count discriminator prefixes (for example, D2's counts), but never does maths.
- **Websocket and gRPC probes** (A12, A13, A23, tier C) are Rust programs in `crates/feed/examples/`, so they become the recorder's own connection code.

| F. Kafka / Redpanda log plus sinks | Yes | Needs a sink anyway | Medium | Heavy | Yes | $0, bigger server | Rejected: one host and one consumer don't need it |

### 6b. The chosen layout
**Layer 0, the raw tape (immutable):**
- Path: `tape/raw/<provider>-<stream>/<YYYY-MM-DD>/<HH>.seg`. The file is written uncompressed while open, then compressed to `.seg.zst` at the hourly rotation. Its SHA-256 goes into `manifest.jsonl`, and the file becomes read-only.
- **Frame layout** (little-endian):
  - magic `TAPE`, version byte, source byte, flags byte, a reserved byte;
  - `recv_wall_ns` u64, `recv_mono_ns` u64, `conn_id` u32, `seq` u64, `payload_len` u32;
  - payload: the protobuf `SubscribeUpdate` bytes **exactly as received**, or the raw JSON of an RPC response such as `getBlock` capture or audit results;
  - `crc32c` u32.
- **Recovery:** scan the open segment and truncate after the last valid checksum.
- A per-segment SQLite index (`signature → segment, offset`) gives fast single-transaction lookups.

**Layer 1, decoded tables (Parquet, zstd, one file per table per hour, written by `tabulate` from closed segments):**
- Tables: `slots`, `txs` (incl. failed, position in block, fee, compute used, priority fee, tips, lookup tables used, receive times), `curve_trades`, `pool_trades`, `migrations` (complete + migrate + create-pool + post-complete-buy), `boost`, `creates` (name, ticker, URI, creator), `token_balance_changes`, `account_updates`, `admin_changes`, `witness_checks`, `unknowns` (raw bytes of anything unrecognised).
- **Column rules:**
  - `u64` → UInt64;
  - `i128` → Decimal128(38, 0) plus a range alarm;
  - public keys → FixedSizeBinary(32), with base58 only in views;
  - times as UTC nanoseconds;
  - every row carries **regime tags**: program deploy slot, IDL SHA-256, decoder version.
- **Re-decoding never overwrites.** It writes `tape/decoded/v<decoder_version>/…`. Old and new versions sit side by side, so results can be compared.
- **Partitioning:** `<table>/date=YYYY-MM-DD/hour=HH/`. DuckDB and Polars read the folder pattern directly.

**Retention and archive:**
- Recent days stay on the recorder disk (the number of days is set from C01's MB/hour).
- Closed segments and Parquet files go to object storage daily. Each copy is checked by SHA-256 before the local copy is deleted (DAT-8).
- Expected volume is 15–135 GB a month raw before compression [UNVERIFIED; C01].

## 8. Testing approach: fixtures, no network
**The rule:** `make test` must pass with networking switched off. CI runs it in a container with no network. This cloud session is already a good imitation. Python tests block sockets in `conftest.py` using only the standard library.

**Fixture kinds** (each file has a `provenance.json`: method, redacted parameters, provider, slot, UTC time fetched, SHA-256):
1. **Real chain data** captured in Phase 0 (`fixtures/chain/`). There must be at least one real transaction for:
   - every event and account type in the IDLs;
   - every instruction that can complete a curve: `buy`, `buy_v2`, `buy_v3`, `buy_exact_sol_in`, `buy_exact_quote_in_v2/v3`, and a `multi_hop_swap` hop (DAT R1 §1);
   - `migrate` and `migrate_v2`, a synthetic migration, a failed 6004 buy, BOOST buy-and-burn, `create_v2` and legacy `create`.

   This is a Gate 0→1 add-on, proposed here.
2. **Raw gRPC frames** (`fixtures/grpc/`): one captured hour from test C01, for recorder and `tabulate` replay.
3. **Account snapshots** (`fixtures/chain/accounts/`): old and new `Pool` lengths, `GlobalConfig`, `Global`, `BondingCurve`, FeeConfig.
4. **Golden vectors** (`fixtures/golden/`): fee and quote inputs with expected outputs. They come from the T6 trades (on-chain truth) and from the SDK referee (hypothetical sizes we never traded).
5. **Hostile fixtures** (`fixtures/hostile/`): shifted, cut-short or over-long bytes, an unknown discriminator, extreme negative `i128`, `u64::MAX`. Each must raise its named alarm (`DECODER_SHAPE`, `UNKNOWN_EVENT`, range).
6. **IDL-diff fixtures** (`fixtures/idl/`): the real Sep 2025 change plus the 5 hostile diffs for RC8.
7. **Replay fixtures** (`fixtures/replay/`): one hour of tape and the expected SHA-256 of every decoded Parquet file. Decoding must be byte-for-byte repeatable.

**Kinds of test:**
- unit tests;
- golden tests;
- property tests (`proptest`);
- **differential tests** (our decoder vs the Codama/SDK referee; in Phase 3, guard builder vs safe-seller builder);
- replay/repeatability tests;
- alarm tests;
- schema-evolution tests (a new IDL version must regenerate cleanly and keep decoding all old fixtures).

Python tests use small Parquet fixtures. Statistical routines are tested with fixed seeds against cases whose answer is known.

**Until the network opens**, synthetic fixtures built from the IDL (labelled `synthetic`) cover decoder shape tests. Real fixtures replace them as soon as test-plan rows A03, A04 and A09 run.

## 9. Dependency pinning and supply chain
**General rules (all ecosystems):**
- Exact versions for direct dependencies, and lockfiles committed.
- Installs only from the lockfile (`--locked`, `--frozen`, `--frozen-lockfile`).
- **A 7-day release-age cooldown** (SEC R1/R2).
- No git or URL dependencies.
- No unofficial "Pump" or "Solana bot" packages, ever.
- Every new dependency needs a one-line reason in `docs/dependencies.md` and a second reviewer.
- **Honest limit:** the `faster_log` crates were online for about 4 months [VERIFIED-SEARCH], so a cooldown alone would not have caught them. The real defences are a short allowlist, review and audits.

| Ecosystem | Where it runs | Controls |
|---|---|---|
| **Rust (Cargo)** | Bot host; guard (Phase 3) | `Cargo.lock` + `cargo build --locked`. Direct dependencies as `=x.y.z`. `cargo deny check` (allowlisted sources: crates.io only; bans: `solana-client`, `solana-sdk`, `anchor-*`, `carbon-*`, `pump-rust-client` outside tests, OpenSSL in favour of rustls [proposal]); `cargo audit` daily; `cargo vet` (audit sets to import: UNVERIFIED); `cargo auditable` embeds the dependency list in each binary. **Cooldown:** until Rust 1.100, `tools/check_cooldown.py` reads each locked crate's `pubtime` from `index.crates.io` and fails CI if any is newer than 7 days. The `pubtime` field exists today [VERIFIED-DOC]. From Rust 1.100 (scheduled 2026-11-12 [VERIFIED-SEARCH]), also set the native option `registry.global-min-publish-age = "7 days"` (name per RFC 3923; confirm at release [UNVERIFIED]). The guard workspace is vendored and diff-reviewed. Crates with build scripts or macros are explicitly allowlisted |
| **Python (uv)** | Bot host, research user only (no access to any secret) | `pyproject.toml` with `[tool.uv] exclude-newer = "7 days"` [VERIFIED-DOC; VERIFIED-LOCAL], `uv.lock` with hashes [VERIFIED-LOCAL], `uv sync --frozen`, exact `==` pins, Python pinned in `.python-version` (3.13) |

- `rust-toolchain.toml` with an exact version;

## 10. Conventions that keep this easy for future AI sessions
- **Small crates**, each with a README that says what it does and how to test it offline.
- One command for everything: `make test`.
- Generated code is marked and regenerated in CI, never edited by hand.
- **Rust style:** no `unsafe`, `clippy` with warnings treated as errors, `rustfmt`, explicit error enums, and no clever macros.
- **Units in every name:** `_lamports`, `_slots`, `_bps`, `_ns`. Every config value is in TOML with its unit.
- **Python style:** type hints, `ruff` (pinned dev tool), one script per study, no notebooks in the repo.
- Every decision and alarm writes a reason code, so humans and AI sessions can read why something happened.
